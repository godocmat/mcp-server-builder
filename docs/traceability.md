# Requirements and acceptance traceability

Phase 0 design · [Product requirements](requirements.md#functional-requirements-and-acceptance-checks) · [Task backlog](../TASKS.md) · [D4 test strategy](testing.md)

These checks apply to the [catalog reference project](requirements.md#reference-project) and the stated platform and fixture profiles. The owning task produces the first passing evidence. The release gate reruns or collects it against the integrated build or final artifact. The checks below are planned.

## Quality measurement

### Coverage denominators

Count executable authored production lines for the selected milestone. The core denominator contains the shared business logic and workflow behavior below. The security-critical denominator is a separately tagged set that can overlap core. Build glue containing an enforcement check belongs in security coverage. Count each executable source line once per denominator across merged test/feature/platform results at the same commit. Report covered and total lines for each component, each language, each milestone denominator and for native or feature-only paths separately. Pilot coverage includes the M4 engineering HTTP binding and excludes v1 code that is outside the selected profile.

| Component and planned source path | Core denominator | Security-critical denominator |
| --- | --- | --- |
| Policy · `crates/mcp-policy/src/**` | Grant and decision rules, limit and redaction behavior | All enforcement, validation, deny reasons, redaction and limit logic |
| Runtime · `crates/mcp-runtime/src/**` | Capability registry, schema validation, dispatch, runtime state, adapter and process behavior | Dispatch authorization, target binding, data and argument validation, credential scoping, cancellation, cleanup and bounds |
| Transport · `crates/mcp-transport/src/**` | Client and server lifecycle, protocol conversion, response and error mapping | Framing and size guards, version/header parsing, request correlation and cancellation, Host/Origin and proxy trust, HTTP auth, sessions and quotas |
| Project · `crates/builder-project/src/**` | Portable schema, migrations, config validation and import | Untrusted parsing and version/size bounds, archive and path validation, import sanitization |
| Application · `crates/builder-app/src/**` | Project, storage, approval, credential and evidence services and entitlement continuity | Catalog/filesystem writes and recovery, approvals, credential providers and account separation, redaction, retention and audit |
| Generator · `crates/builder-generator/src/**` | Rendering, version and lock selection, plan and regenerate behavior | Destination confinement, safe template serialization, reviewed dependency/source identity, write/replacement safety and secret-free exports |
| Playground · `crates/builder-playground/src/**` | Connection, process, scenario, report and trace workflows | Launch trust, local supervision, OAuth discovery/callback/refresh, fixture/live separation, cancellation and evidence sanitization |
| Native shells · `apps/cli/src/**`, `apps/desktop/src-tauri/src/**` | Command dispatch, DTO/diagnostic mapping, picker and workflow coordination | IPC allowlist, path and approval handoffs, headless denial, output boundary and any native credential entry paths |
| Desktop · `apps/desktop/ui/src/**` | Angular application state, validation feedback, editing, launch review, replay, export and recovery workflows | Credential-entry clearing, approval controls and inert untrusted rendering paths |

As implementation lands, each task owner maps real files or modules to the table. F2 collects Rust line coverage with `cargo-llvm-cov` and Angular line coverage with the pinned Angular test runner. R3 reconciles the path inventory before the candidate calculation. Exclude generated DTOs, dependency/vendor sources, test code, synthetic fixtures, declarative package assets and duplicate emitted copies of covered runtime code. Exercise emitted code through clean generation and standalone runs. Record every additional exclusion with file path, reason and reviewer. Keep unexercised authored code in scope. An unavailable native or feature report is an evidence gap. [D4 coverage and CI plan](testing.md#ci-and-release-evidence)

### Performance method and budgets

Use D4's 4 vCPU, 8 GiB, local SSD reference machine, a prebuilt release server, and the local catalog upstream fixture. Record OS/build, CPU, memory, storage, fixture revision, binary/commit, SDK, transport and protocol revision, and raw results including failed attempts. Measure each applicable revision and transport profile. For v1 HTTPS, use the local reference ingress, a valid scoped token and warmed provider metadata for call timing. Pace requests within the reference quota and record the pacing outside the round-trip measurements. R1 verifies admission limits separately. Record connection reuse and keep installation, compilation, browser sign-in and TLS/auth setup as separate measurements. Use nearest-rank p95 at the sorted observation `ceil(0.95 × n)`. [D4 benchmark procedure](testing.md#proposed-performance-budgets)

| Measure | Method | Target |
| --- | --- | --- |
| Start to discovery | 30 fresh server processes. Time launch request through successful `server/discover` or legacy initialize and catalog discovery. | p95 ≤ 2 s |
| `lookup_item` round trip | Call item `42` 20 times for warm-up, then measure 200 sequential calls through receipt of the complete reply. | p95 ≤ 100 ms stdio, ≤ 150 ms HTTPS |
| Idle server memory | Measure server RSS or Windows working set after 60 seconds idle. Record the tool and process scope. | ≤ 128 MiB on each reference run |
| Explicit local stop | Measure stop to exit and reap after a normal run and after canceling a slow call. Run ten consecutive repetitions per path. | ≤ 5 s each with zero owned descendants |

R1 measures service drain and restore separately against the agreed shutdown deadline and recovery targets. M10 supplies pilot measurements and R4 repeats against the candidate on matched hardware. Document any workload or hardware variance with the results. [Runtime limits](contracts.md#cancellation-deadlines-and-limits) · [Recovery targets](../DECISIONS.md#adr-009--ingress-rollout-and-recovery)

## Evidence records

For each gate, record requirement and task IDs, commit, artifact checksum or digest, fixture revision, commands, observed result and evidence location. Include target OS, architecture, filesystem and WebView as relevant, and for MCP add client build/runtime, SDK features, endpoint profile, actual revision, provider image and authentication/registration mode. Record failing or blocked runs with the gap, responsible owner and release disposition. Support claims require passing evidence for the named combination. R5 collects the full matrix and the installation, development, troubleshooting, operations, contribution, changelog and licensing documentation required for release.
