# Test strategy and release evidence

Phase 0 · D4 · 12 November 2026

Use the same catalog project from the clean Windows pilot install through CLI replay, independent Rust build, and v1 Linux deployment. The cases below assign evidence to the task that first produces it and to the release gates that rerun it. The platform matrix and quality budgets are proposed. [Product requirements](requirements.md#functional-requirements-and-acceptance-checks) · [Task backlog](../TASKS.md) · [Deployment and platform matrix](deployment.md#proposed-platform-targets)

## Reference fixtures

- Configure `lookup_item` with a string `id` and an object result. A deterministic REST fixture returns `Sample item` for `42`. Read the catalog guide and an expanded per-item resource URI from a temporary granted root. Render the review prompt with the item ID. Save a passing scenario, an expectation mismatch, an invalid argument and a denied permission. Add a cancellable fixture call, an upstream failure, and fixture counters for dispatch, active work and protected effects.
- Use real UTF-8 JSON-RPC subprocess pipes and real loopback HTTP sockets. Drive both with a small independent wire harness and run a separate Inspector smoke. Stub upstream behavior with controlled services. Give HTTPS fixtures a trusted test CA or a valid test certificate. Use dedicated disposable roots, ports, databases, OAuth clients and synthetic credentials for concurrent runs. Keep reusable fixtures and expected results versioned and free of live data.
- For commercial v1, deploy the generated catalog behind the selected ingress and use real provider-issued access tokens. Seed a second caller with narrower permissions, a second MCP resource under the same issuer and per-adapter fixtures for SQLite, PostgreSQL, Git, custom Rust and approved executables. Observe the actual adapter or process state before and after each denial. [Reference project](requirements.md#reference-project) · [D3 verification](security.md#verification-cases)

## Proposed performance budgets

Start with the requirements' 4 vCPU, 8 GiB, local SSD reference machine, a prebuilt release binary and a local REST upstream. Record CPU, OS and build, memory, storage, fixture revision and versions. For v1 use local HTTPS through the reference ingress, a valid scoped token and warmed provider metadata. Keep installer time, compilation and browser sign-in in separate measurements. Use matched reference machines for gate comparisons and record any hardware or workload variance. [Requirements budgets](requirements.md#quality-and-release-evidence)

| Measure | Method and proposed target |
| --- | --- |
| Start to discovery | Measure launch request to successful discovery on 30 fresh processes. Use `server/discover` on the modern profile or the legacy handshake followed by successful discovery of the catalog. Report the revision and p95, proposed at most **2 s**. |
| `lookup_item` round trip | Use the same `42` input for 20 warm-up calls and then 200 sequential measured calls per profile. Measure from the client through receipt of the complete result. Proposed p95 at most **100 ms** over stdio and **150 ms** over HTTPS. Record connection reuse and TLS/auth setup separately. |
| Idle server memory | Record resident memory after 60 seconds idle, using the platform RSS or Windows working set for the server process. Proposed at most **128 MiB** per reference run. Record the measurement tool and process scope. |
| Explicit stop | Measure from stop request to exit and reap, after a normal run and after canceling a slow call. Run ten consecutive repetitions per path. Proposed at most **5 s** each with zero owned descendants. Record process identities and exit times. Record remote supervisor drain results separately against R1's agreed deadlines. |

Keep raw samples and use nearest-rank p95, the observation at `ceil(0.95 × n)` in sorted order. Record failed attempts alongside timings. D5 approves the starting budgets and measurement contract. M10 and R4 supply the observed pilot and release candidate results.
