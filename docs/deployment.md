# Deployment and release plan

The desktop release includes the builder and CLI for local stdio workflows. The later sections describe a proposed remote HTTP deployment profile. [Product plan](../PLAN.md) · [Testing plan](testing.md)

## Desktop package targets

| Package | Target environment | CLI path |
| --- | --- | --- |
| Windows NSIS `.exe` | Windows x64 with WebView2, built on `windows-2025`. | `mcp-builder.exe` beside the desktop executable. |
| macOS `.dmg` | Apple silicon with WKWebView, built on `macos-26` arm64. | `/Applications/MCP Server Builder.app/Contents/MacOS/mcp-builder` after the app is copied into Applications. |
| Ubuntu `.deb` | Ubuntu 24.04 amd64 with WebKitGTK, built on `ubuntu-24.04`. | `/usr/bin/mcp-builder`, also available as `mcp-builder` on `PATH`. |

Each release ZIP includes the native installer, `SHA256SUMS.txt` for the extracted installer, the source commit in `BUILD-INFO.txt`, and distribution notices. Match the published `.zip.sha256` companion to the ZIP before extracting it. Use `shasum -a 256 -c` on macOS or `sha256sum -c` on Ubuntu with the checksum filename, or use `Get-FileHash -Algorithm SHA256` on Windows with the ZIP filename. Run checksum-file commands from the directory that contains the named download. [GitHub Releases](https://github.com/godocmat/mcp-server-builder/releases)

Open the DMG on macOS and drag **MCP Server Builder** into Applications. This DMG contains an ad hoc signed, unnotarized app. If macOS blocks first launch, verify the download and use **System Settings → Privacy & Security → Open Anyway** for this app if your device policy permits it. [Apple's instructions for opening an app from an unidentified developer](https://support.apple.com/en-us/102445)

On Ubuntu run `sudo apt install ./mcp-server-builder-0.2.0-linux-x64.deb` from the directory where you extracted the ZIP for v0.2.0. APT resolves the package's runtime dependencies. Open **MCP Server Builder** from the applications menu. Remove the installation with `sudo apt remove mcp-server-builder`.

## Build the Windows pilot installer

Use Windows x64, PowerShell 7.3 or newer, and the locked Rust and Node inputs and MSVC prerequisites. Install the Angular dependencies from the lockfile before building. [Windows development prerequisites](development.md#windows-prerequisites-and-local-setup)

```powershell
Push-Location apps/desktop
npm.cmd ci --engine-strict
Pop-Location
./apps/desktop/scripts/build-windows-pilot.ps1
```

The script builds the release CLI and desktop from the same checkout. It stages the CLI for Tauri and creates an unsigned per-user NSIS installer under `x86_64-pc-windows-msvc/release/bundle/nsis` in the Cargo target directory. Pass `-TargetDirectory` to choose the output location. The Windows package places `mcp-builder.exe` beside the desktop executable. That copy serves as the managed playground worker and can also be invoked directly from PowerShell. The bundled CLI follows the same approval requirements as a source build. [CLI workflow](local-cli.md)

On the Windows acceptance VM, record the installer SHA-256, signing status, and WebView2 version before completing the pilot workflow. The installer uses Evergreen WebView2 when present and downloads Microsoft's bootstrapper when the runtime is missing. [Windows pilot checklist](windows-pilot.md)

## Build the macOS or Ubuntu installer

Use the platform-native build tools, PowerShell 7.3 or later, and the locked Rust and Node versions. Install the Xcode Command Line Tools on macOS or the Tauri Debian development libraries on Ubuntu.

```powershell
Push-Location apps/desktop
npm ci --engine-strict
Pop-Location
./apps/desktop/scripts/build-unix-release.ps1
```

The script builds and stages the first-party `mcp-builder` CLI before invoking Tauri with the native installer target. The DMG is under `aarch64-apple-darwin/release/bundle/dmg` and the DEB is under `x86_64-unknown-linux-gnu/release/bundle/deb` in the Cargo target directory. Pass `-TargetDirectory` to choose the output location. [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/)

## Hosted installer verification

Dispatch **Desktop release installers** on the release commit or push to a `codex/release-*` branch. On each disposable runner, it installs that checkout's native package, checks the packaged CLI, exercises the catalog's fixture replay and builds and tests a standalone export. Windows uses native UI Automation to exercise the installed playground. macOS and Ubuntu verify the window of the installed application and run the desktop IPC playground checks with the first-party worker in Foundation CI. The installer job checks package removal and confirms the portable project remains. A job uploads its ZIP and SHA-256 companion after the checks pass. [Desktop installer workflow](../.github/workflows/windows-pilot.yml) · [Foundation checks](ci.md)

## Generated Linux service

Propose a single generated MCP process per operator-owned project behind NGINX. The public MCP URL and authorization issuer have configured HTTPS origins. The provider and its database have independent lifecycle and state. A single backend also gives an issued legacy session one owner. R1 exercises restart and reinitialization before any multi-instance profile is considered. [D1 transport profiles](mcp-compatibility.md#transport-lifecycles) · [D3 system model](security.md#system-model)

| Concern | Native systemd profile | Docker Compose profile |
| --- | --- | --- |
| Install and run | Build the export with pinned Rust and `cargo build --release --locked` on the baseline. Install a versioned binary under `/opt/<service>/releases/`, operator-owned configuration under `/etc/<service>/` and service state under `/var/lib/<service>/`. Run under a dedicated unprivileged identity. Grant write access only to required state and runtime directories. Bind the MCP backend and its health routes to loopback. | Use a multi-stage Dockerfile with pinned build and runtime base digests and a compatible Ubuntu 24.04 runtime with CA roots and required shared libraries. Copy the locked release binary and required runtime assets into the final image. Run with a fixed unprivileged UID/GID, read-only root filesystem, and explicit writable volume or tmpfs paths. Use exec-form startup. Only the ingress publishes a host port for the MCP service. |
| Network and data | Ingress connects to the loopback backend. Mount operator-approved inputs read-only where possible. The runtime can reach the configured issuer and granted adapters. Restrict the database and provider management endpoints to their intended operators and services. | Put ingress and MCP on a private backend network and keep the provider database on a separate network. Restrict egress to required issuer and adapter traffic using the deployment's network controls and runtime policy. Keep persistent state in named volumes or documented bind mounts. An app or provider container replacement reuses its designated state. |
| Secrets | Inject deployment secrets through restricted files, using systemd `LoadCredential=` when applicable, or documented explicit environment injection. Check actual access from the service identity, including after rotation. | Grant each service the specific Compose secrets it reads. Compose uses bind mounts for file-backed secrets, so set ownership and permissions on the source and verify readability as the actual container user. |

Keep portable manifests, Dockerfile layers, Compose examples and version control to secret references. Separate TLS keys, provider database credentials, issuer keys, inbound MCP tokens and outbound adapter secrets by purpose and reader. Document rotation and restart or reload behavior for each. Verify credential injection and rotation with synthetic canaries. Check image history, configuration output, service logs, backups and exported evidence for unintended copies. [systemd execution settings](https://manpages.ubuntu.com/manpages/noble/en/man5/systemd.exec.5.html) · [Docker multi-stage builds and pinning](https://docs.docker.com/build/building/best-practices/) · [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/) · [Compose service reference](https://docs.docker.com/reference/compose-file/services/#secrets) · [D3 credentials](security.md#local-workflows-and-credentials)

### TLS and ingress

Provision DNS and a trusted TLS certificate for the MCP and issuer endpoints, with a documented renewal path. Use TLS termination at NGINX and a private same-host or Compose upstream. For example, `https://mcp.example.com/mcp` is the configured resource and `https://mcp.example.com/.well-known/oauth-protected-resource/mcp` is its metadata URL. Publish the metadata and 401 Bearer challenge from the resource server. Route the provider's discovery, sign-in and token endpoints on the configured issuer origin and restrict its administration surface. Verify the certificate chain and hostname from a supported client, including the selected private CA workflow where supported. [RFC 9728 metadata paths](https://www.rfc-editor.org/rfc/rfc9728.html#section-3.1) · [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) · [D3 resource server](security.md#authenticated-streamable-http)

- Allow only configured public hosts and trust forwarded information only from the controlled ingress. Strip or overwrite client-supplied forwarding headers and derive issuer, resource, audience and metadata URLs from configuration. Preserve `Authorization`, protocol routing headers, `Origin`, and legacy session headers through the proxy. Pass through the backend status and `WWW-Authenticate` challenge. Enforce the configured Origin allowlist, header/body parity and per-request authentication and authorization on both revisions. Exercise allowed, missing and invalid `Origin`, direct-backend reachability and spoofed forwarding headers. [D1 HTTP rules](mcp-compatibility.md#transport-lifecycles) · [D3 ingress verification](security.md#tm-007-http-ingress-and-resource-server)
- Disable proxy response buffering and caching on MCP streams. Preserve the response media type and stream progress as it arrives. Turn off upstream retries on the MCP route so the proxy cannot replay a call. Set ingress body, connection and admission limits, and enforce per-principal quotas, concurrency, deadlines and stream lifetime in the runtime. Align proxy idle timeouts with permitted gaps between response events. R1 proves modern disconnect cancellation and legacy explicit cancellation through NGINX with another call in flight. [NGINX proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html) · [D1 cancellation](mcp-compatibility.md#errors-timeouts-and-cancellation)
- Trial issued, in-memory compatibility sessions first, subject to M4 results. Bind each session to the verified principal and client, authenticate every use, and expire protected streams at the authorization boundary. Verify that an old session receives HTTP 404 after restart and the client can initialize again. Modern calls continue through a fresh connection with per-request metadata. [D1 legacy behavior](mcp-compatibility.md#2025-11-25) · [D3 ingress verification](security.md#tm-007-http-ingress-and-resource-server)

### Authorization provider

Use **Logto OSS** as the provisional reference. Run a pinned, patched deployment with durable PostgreSQL on a private network and configure the exact production issuer (`ENDPOINT`) and restricted admin endpoint. Start with a pre-registered public PKCE client, configured API resource equal to the canonical MCP URL, and least-privilege scopes. Record provider image, database major version, resource/audience, callback URIs and registration mode. Prove issuer and callback validation, rotation and revocation behavior, and `resource` binding through token refresh using two MCP resources under the same issuer. Exercise CIMD if a target client uses it, including outbound fetch controls and the provider's refresh settings. Use durable production database setup in R1. [Logto OSS production configuration](https://docs.logto.io/logto-oss/deployment-and-configuration) · [Logto API resources](https://docs.logto.io/authorization/global-api-resources) · [Logto CIMD](https://docs.logto.io/integrate-logto/third-party-applications/dynamic-apps) · [D3 shortlist](security.md#self-hostable-oauth-provider-shortlist)

Keep **Keycloak** as the provisional fallback if the reference fails a required flow. Trial a patched production image with an explicit HTTPS hostname, trusted proxy settings and a durable external PostgreSQL database. Its `resource-indicators` and `cimd` features are experimental. Enable only the features a candidate profile needs and test their behavior through an upgrade. Where a supported client needs DCR, exercise restricted registration and the same audience, callback and refresh checks before claiming that combination. Use actual provider metadata and client behavior to choose the supported profile. [Keycloak production containers](https://www.keycloak.org/server/containers) · [Keycloak reverse proxy](https://www.keycloak.org/server/reverseproxy) · [Keycloak MCP features](https://www.keycloak.org/securing-apps/mcp-authz-server) · [Keycloak registration policy](https://www.keycloak.org/securing-apps/client-registration)

### Health, logs and shutdown

- Propose private `/livez` and `/readyz` endpoints. Liveness reports that the process is running and responsive. Readiness requires valid configuration and policy, required local state and usable issuer verification material. Readiness drops while draining or when required verification state is unusable. Check provider readiness independently. Exercise startup with missing secrets, expired verification state, temporary issuer loss with still-valid cached keys, and recovery. Record the selected key rotation and staleness behavior. Keep probe responses limited to status and expose them only to the operator or service supervisor. [D3 token validation](security.md#authenticated-streamable-http) · [Compose health checks](https://docs.docker.com/reference/compose-file/services/#healthcheck)
- Write structured sanitized service logs to journald or the configured container log driver. Keep correlation IDs and the D3 audit fields, apply retention and file or volume access limits, and configure ingress logs to omit credentials and OAuth callback parameters. Measure whether records remain available across the restart, upgrade and restore operations promised in the runbook. [D3 evidence](security.md#local-workflows-and-credentials)
- On SIGTERM, drop readiness and close admission, finish eligible work within a drain deadline, then cancel outstanding calls, close streams and sessions, and reap owned workers. Flush bounded audit and state writes before exit. Set systemd `TimeoutStopSec=` or Compose `stop_grace_period` beyond the application deadline. Trial systemd `KillMode=mixed` for a main-process drain with cgroup cleanup. For Compose, verify that the main process receives SIGTERM and that child reaping works with the selected PID 1 or `init: true` profile. Test normal and forced stops from the actual supervisor with both active and idle connections. [systemd kill modes](https://manpages.ubuntu.com/manpages/noble/en/man5/systemd.kill.5.html) · [Compose stop and init settings](https://docs.docker.com/reference/compose-file/services/) · [Shutdown checks](testing.md#deployment-smoke-and-recovery)

### Persistence and operations drill

Inventory the generated config and policy, artifact versions, adapter state and approved inputs, retained audit data, provider database, and the keys or secret references needed to recover. Store durable state outside the binary, container and temporary directories. Keep builder project data and OS credentials on the builder side. Keep server, provider, and adapter data in separately owned stores. The provider's PostgreSQL is its identity store. A generated PostgreSQL adapter uses its own scoped database or role. In-memory MCP sessions are re-established after restart.

R1 runs this drill on both Linux profiles. R3 repeats recovery and failure cases and R5 follows the published instructions with the candidate artifacts. Record commands, versions and digests, sanitized evidence, and actual data loss and time to recover.

1. **Install and seed.** On a clean host, start the provider and generated catalog service from the documented inputs. Check health and a real authorized MCP call, then confirm a denied call leaves upstream state intact. Record a known data marker and verify it survives service restart or container replacement.
2. **Back up and verify.** Record binary/image and schema versions and back up before changes. Use a PostgreSQL backup with the matching restore procedure and roles or other required globals, including the provider database. Take a consistent SQLite backup through its backup API or while quiesced, including any enabled audit or adapter database. Capture approved files, deploy config, and required provider key material or secret references. Keep backups access-controlled and encrypted. Validate restore inputs and integrity before changing the active service. [PostgreSQL `pg_dump`](https://www.postgresql.org/docs/current/app-pgdump.html) · [PostgreSQL roles and globals](https://www.postgresql.org/docs/current/app-pg-dumpall.html) · [SQLite backup API](https://sqlite.org/backup.html)
3. **Upgrade.** Rehearse upgrades from the previous supported version or a saved prerelease build with representative state for the first release. Upgrade the issuer separately using its matching migration instructions. Drain and stop, apply the versioned changes, confirm readiness, then obtain fresh authorization and repeat allow, deny, and data-marker checks. Compare persisted state and required audit records. [Logto OSS upgrade procedure](https://docs.logto.io/logto-oss/upgrading-oss-version)
4. **Roll back and restore.** Inject a failing rollout or migration. Revert the binary or image digest and configuration for a compatible schema. If a migration prevents in-place downgrade, restore the matching backup with the older runtime or provider version into clean state. Restore the backup into an isolated clean host or Compose project to prove it can recover independently. Preserve issuer and resource identifiers in the isolated environment, authenticate again, read the marker, test denial and verify the expected audit evidence. Record data written after the backup and measure the recovery time and data-loss window against the targets D5 selects.
