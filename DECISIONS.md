# Architecture decision records

12 November 2026 · D5 Phase 0 · [Architecture](docs/architecture.md) · [Contracts](docs/contracts.md) · [Implementation backlog](TASKS.md)

These records select the implementation starting point. A selected contract defines the intended product behavior. Candidate dependencies and support profiles require the named evidence before promotion to a released claim. Record the tested input, commit, result and any superseding decision as evidence arrives.

## ADR-001 · Shared workspace and application services

**Status** Selected. The CLI and desktop need identical project, validation, trust and generation behavior. Use a Cargo workspace with thin Clap and Tauri shells over shared Rust services, Angular over typed IPC, and reusable runtime and transport crates for preview and generated servers. Keep deployment to one service process per project with a separate external issuer. The workspace dependency direction avoids coupling generated code to the builder's catalog, GUI or entitlements. [Component ownership](docs/architecture.md#components-and-workspace-boundaries)

**Verification** F1 records the crate graph and proves a clean local build, minimal Angular/Tauri launch and CLI JSON smoke. F2 repeats builds on the three target runners and checks the DTO contract. M10 and V11/V12 compare actual diagnostics and policy decisions across shells. [Task backlog](TASKS.md#discovery-and-foundation)

## ADR-002 · Dual-revision MCP and SDK boundary

**Status** Contract selected. SDK pin provisional. Target `2026-07-28` and `2025-11-25` on both transports, with one shared registry and object-shaped tool input and output schemas. Ship a fixed catalog through v1. Advertise the core capability methods, applicable lifecycle notifications and request-scoped progress. Defer change subscriptions, modern-only scalar/array portable output and the optional features listed in the contracts. Windows MVP ships stdio. Loopback HTTP is an engineering gate. V1 adds authenticated Streamable HTTP. [D1 capability and wire evidence](docs/mcp-compatibility.md#capability-baseline) · [Transport contract](docs/contracts.md#mcp-transport-and-execution)

Use issued in-memory legacy HTTP sessions for explicit request cancellation and predictable lifecycle. Support owner DELETE, return 405 for standalone GET, and omit resumption. The modern path remains stateless on the same deployment. Keep sessions out of durable state and reinitialize after restart. M4 tests the sessionless SDK path as a comparison, including explicit cancellation and stream-drop semantics. Changing the release profile requires the same wire and client evidence. [D1 lifecycle](docs/mcp-compatibility.md#transport-lifecycles)

F1 starts with exact `rmcp = "=3.9.0"` for its build probe and keeps its types in `mcp-transport`. Enable `server` and `transport-io` for stdio, then evaluate `transport-streamable-http-server` for HTTP. The playground uses a separate client feature set with `transport-child-process`, then `transport-streamable-http-client-reqwest` and `auth` for remote use. Select TLS explicitly. Use 3.8.0 as a comparison if a regression appears. M3/M4 own the final SDK/feature recommendation and lock evidence. A gap needs a verified boundary fix or a documented pin change before the affected gate passes. [Tagged release](https://github.com/modelcontextprotocol/rust-sdk/releases/tag/rmcp-v3.9.0) · [D1 feature and wire checks](docs/mcp-compatibility.md#rust-sdk-candidate)

**Verification** M3/M4 exercise independent raw pipes and sockets for all four combinations, version errors, fallback, schema and result mapping, cancellation, header parity, and issued-session lifecycle. R1 repeats HTTP through ingress. V10/R4 record client versions and actual revisions before claims appear in the support matrix. [Wire matrix](docs/testing.md#wire-and-client-interoperability)

## ADR-004 · Approval, credentials and policy enforcement

**Status** Selected. A portable project asks for access. The local operator or deployment policy grants it. Approvals bind exact reviewed operation, local owner, executable or source identity, arguments, working directory, environment references and policy. Use one-use approval in the pilot and explicit revocable reuse in v1. Evaluate the same typed grants for GUI and CLI, preview and generated execution. Recheck at the concrete target before effects and credential use. Treat imported or custom Rust source as trusted code only after explicit build and launch approval. [Threat boundaries](docs/security.md#trust-boundaries-and-threats) · [Approval contract](docs/contracts.md#policy-approvals-and-credentials)

Bind credential names to one selected source. Start with explicit environment or session-only values, then add Windows Credential Manager, macOS Keychain and Linux Secret Service with explicit fallback. Deployment uses restricted secret files by default and supports explicit environment binding. Keep evidence metadata-only by default, with bounded sanitized payloads opt-in. Credential injection, redaction and rotations use synthetic canaries before release. [Evidence format and limits](docs/contracts.md#scenarios-results-and-evidence)

**Verification** M2/M5/M7 prove deny-before-effects and pilot reference handling. V2 verifies native credentials, cross-project scope, approval invalidation, rotation, retention and fallback. V5–V9 verify adapter constraints and trusted-code approval. R1/R3 confirm secret injection and absence of canary values in evidence and artifacts. [TM-002–TM-006](docs/security.md#verification-cases)

## ADR-005 · Execution and cancellation

**Status** Selected contract, native enforcement candidates. Translate the binding-specific cancellation signal to one runtime token and deadline. Bound work even during progress and preserve unrelated requests. A cancellation result records whether the effect committed, did not occur or is unknown. Require operator review before replaying a live effect with an unknown outcome. Use Windows Job Objects assigned before work, with breakaway disabled, and trial process groups on macOS/Linux for cooperative processes. The supported executable profile depends on native tests of argument handling, ownership and descendant cleanup. [Cancellation and limits](docs/contracts.md#cancellation-deadlines-and-limits) · [Native supervision design](docs/security.md#local-workflows-and-credentials)

**Verification** M3/M4 prove two concurrent requests with only the canceled work torn down. M5 and V5 confirm I/O and transaction cleanup. M7 and V8 test explicit stop, failed assignment or start, process exit and descendant behavior. V8/R3/R4 publish the verified process class and OS boundary for approved executables. R1 checks modern disconnect and legacy explicit cancellation through NGINX. [Native verification cases](docs/testing.md#security-and-native-checks)

## ADR-006 · Standalone generation and license continuity

**Status** Distribution model selected. License terms proposed for owner review. Bundle source for the versioned runtime and server transport as Cargo path dependencies. Ship locked inputs, real handlers, standalone tests and provenance. Regeneration stages a new output, carries reviewed project-owned code forward and flags edited generated files. A prior export remains buildable independently. Record runtime and template versions, publish security fix notices and provide regeneration and upgrade instructions with fixes. [Generation contract](docs/contracts.md#standalone-output-and-regeneration)

Propose Apache-2.0 for builder-owned bundled runtime and emitted scaffolding, with third-party notices and retained terms. Product owns the builder distribution license and the final generated-code and runtime grant. Project inputs and customer-authored sources follow their owners' terms. M6 inventories the bundled components. V9 and R2 record the final dependency and license inventory and SBOM. R5 requires the approved redistribution terms and notices before public distribution. [Commercial licensing requirements](docs/commercial-model.md#licensing-and-continuity-requirements)

Keep entitlements in the builder and restrict them to optional paid features. Core project access, editing, validation, testing, recovery, security and source export work with missing, expired or unreachable entitlements. V13 owns continuity through the shared services and R5 verifies a previously exported server with the builder and licensing endpoint absent. Use the D2 cohort, reference project and success thresholds at the M10 pilot debrief. Product owns measured positioning and price hypotheses, with a separate decision for paid offers, hosted services and payment integration. ## ADR-007 · External OAuth and client profiles

**Status** Contract selected. Reference provider and client support provisional. Use an external authorization server and a generated JWT resource server. Start with Logto OSS and a durable PostgreSQL database. Use a public pre-registered client with PKCE S256, the exact loopback callback, and the public MCP URI as resource and audience. Verify issuer metadata, token type, scopes, caller mapping and the provider's access-token client identifier before accepting session binding. Start the reference trial with a five-minute access token lifetime and 15-minute maximum trusted JWKS cache age. Refresh on an unknown key through a bounded issuer lookup. Fail closed when usable verification material is unavailable. Revoked refresh stops new tokens. A previously issued valid access token may remain usable until expiry. Protected streams end by token expiry. [Security design and provider shortlist](docs/security.md#authenticated-streamable-http) · [Logto resource configuration](https://docs.logto.io/authorization/global-api-resources)

Pre-register first for each candidate that supports it. Trial CIMD when a selected client needs it, with approved provider fetch destinations and a proven public-client refresh profile. Keep DCR disabled in the reference profile. If a required client cannot use pre-registration or verified CIMD, V3/V4/V10 trial a restricted DCR profile on Keycloak and repeat the resource, discovery, callback, upgrade and refresh gates. Keycloak also remains the fallback if Logto cannot pass the required resource and refresh tests. The release supports only the selected, tested provider and registration combinations. [D3 provider shortlist](docs/security.md#self-hostable-oauth-provider-shortlist) · [Logto CIMD](https://docs.logto.io/integrate-logto/third-party-applications/dynamic-apps) · [Keycloak MCP guidance](https://www.keycloak.org/securing-apps/mcp-authz-server)

## ADR-009 · Ingress, rollout and recovery

**Status** Reference profile selected. Use NGINX with TLS termination and a private upstream, explicit Host/Origin and trusted proxy handling, preserved auth and MCP headers, and SSE buffering, caching and upstream retries disabled. Keep health routes private. `/livez` reports process responsiveness. `/readyz` requires valid config and policy, required local state and usable issuer verification material. Drop readiness during drain. Deploy one instance per project and keep legacy sessions in memory. [Ingress and health profiles](docs/deployment.md#tls-and-ingress) · [Default limits](docs/contracts.md#cancellation-deadlines-and-limits)

Start with the restricted Windows pilot at M10. Stage the v1 release candidate for clean install and an operator rehearsal on both Linux profiles. R5 promotes the verified checksummed artifacts after release authorization. Stop a rollout when a readiness, allow/deny or persisted-marker check fails. Restore the prior verified state before retrying.

Version binary/image, operator configuration and state format together in the rollout record. Snapshot consistent state before changes and take a scheduled daily backup of required durable state. Back up operator config, audit state, adapter data, and the issuer database and required key material with separate owner scopes. Local project recovery uses its committed manifest and known-good backup. Server recovery uses the matching verified artifact, config and backup. Revert artifact and config on failed rollout when the schema is compatible, or restore matching state into a clean target. Issue fresh authorization after restart or restore. Reference targets are at most 24 hours of lost durable data and at most 60 minutes to restore from declared failure to readiness, an authorized call, a denial and a verified data marker. Record actual loss and time under both Linux profiles. [D4 operations drill](docs/deployment.md#persistence-and-operations-drill)

**Verification** R1 runs install, credential rotation, provider loss/recovery, active drain, upgrade, rollback and isolated restore with versioned inputs. R3 injects failures and checks backups, redaction and retention. R5 repeats from final artifacts and checks the rollout and rollback runbook. [Deployment smoke](docs/testing.md#deployment-smoke-and-recovery)
